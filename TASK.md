# Техническое задание: Yandex Music Discord Presence

**Версия документа:** 1.0  
**Статус:** исходное ТЗ для агентской разработки  
**Целевая платформа первого релиза:** Windows 10/11 x64  
**Стек:** Tauri 2, Rust, Vue 3, TypeScript, Vite  
**Рабочее название:** `Yandex Music Presence` (название должно быть централизованно настраиваемым)

---

## 1. Цель проекта

Разработать лёгкое desktop-приложение для Windows, которое определяет, что пользователь слушает в Яндекс Музыке, и публикует эту информацию в Discord через Rich Presence. Приложение должно работать в фоне из системного трея, иметь современный интерфейс на Vue 3 и потреблять минимум ресурсов в простое.

Приложение не является музыкальным плеером и не должно управлять воспроизведением. Его задача — считывать текущее состояние воспроизведения, преобразовывать его в Discord Activity и отображать соединения/настройки в пользовательском интерфейсе.

### 1.1. Основной пользовательский сценарий

1. Пользователь устанавливает и запускает приложение.
2. Вставляет OAuth-токен Яндекс Музыки в поле с защищённым вводом и сохраняет его.
3. Приложение проверяет токен и устанавливает соединение с Ynison — неофициальным real-time протоколом синхронизации воспроизведения Яндекс Музыки.
4. Если в аккаунте Яндекс Музыки есть активное воспроизведение, приложение получает трек и его метаданные.
5. Приложение подключается к запущенному desktop-клиенту Discord через локальный IPC и публикует активность типа `Listening`.
6. При смене трека, паузе, возобновлении или остановке приложение обновляет/очищает Discord Presence.
7. Окно можно скрыть; приложение продолжает работать из системного трея.

### 1.2. Что значит «лёгкое приложение»

- Не использовать Electron, Node.js runtime в production или отдельный Go/Python sidecar.
- Основная логика, сеть и IPC реализуются в Rust.
- Vue используется только для интерфейса внутри системного WebView2.
- Не опрашивать API Яндекс Музыки каждую секунду.
- Предпочитать одно долгоживущее WebSocket-соединение Ynison и событийную обработку.
- Не обновлять Discord RPC без реального изменения активности.
- Не загружать и не хранить в оперативной памяти ненужные изображения/ответы API.
- Не держать постоянный JavaScript-таймер, если окно закрыто и визуальный прогресс не нужен.

Окончательные показатели RAM зависят от версии WebView2 и системы. Их необходимо измерять на реальной сборке, а не обещать заранее.

## 2. Границы проекта

### 2.1. Входит в MVP

- Windows 10/11, x64.
- Tauri 2 + Rust + Vue 3 + TypeScript + Vite.
- Подключение к Яндекс Музыке с использованием OAuth-токена.
- Получение playback state через Ynison.
- Чтение метаданных трека, включая название, исполнителей, альбом, ID, длительность, позицию, состояние воспроизведения и URL обложки — если соответствующие поля доступны в текущем ответе протокола/API.
- Получение расширенных метаданных по track ID, если Ynison их не предоставляет.
- Подключение к Discord через локальный RPC IPC; бот и Discord bot token не нужны.
- Rich Presence со статусом Listening, названием трека, исполнителем, доступным таймингом и обложкой, если динамический artwork поддерживается используемым RPC-путём.
- Современный интерфейс на русском языке.
- Системный трей, сворачивание в трей, меню быстрого управления.
- Настройки и защищённое хранение OAuth-токена.
- Автоматическое переподключение и понятное отображение ошибок.
- Логи с редактированием чувствительных данных.
- Unit-тесты для моделей, преобразования состояния и построения Presence; тесты обработки фикстур Ynison.
- Документация для разработки, сборки и настройки Discord Application ID.

### 2.2. Не входит в MVP

- Воспроизведение, пауза, перемотка, управление очередью или громкостью Яндекс Музыки.
- Поддержка Spotify, Apple Music, YouTube Music и других сервисов.
- Поиск соответствий треков через iTunes/Deezer или fuzzy matching. В основном потоке используется идентификатор трека из Ynison.
- Отдельный сервер или облачный backend разработчика.
- Сбор телеметрии, аналитики и пользовательских данных.
- Пользовательские Discord-аккаунты/токены. Запрещено просить Discord user token или имитировать пользовательскую сессию.
- macOS/Linux в первом релизе. Архитектуру не следует искусственно связывать с Windows там, где можно оставить платформенную абстракцию, но поддержку других OS сейчас не реализовывать.
- Фоновая служба Windows без пользовательской сессии.
- Автоматическая передача пароля Яндекса приложению.

### 2.3. Предусмотреть как расширения, но не реализовывать без необходимости

- Дополнительный источник Windows Global System Media Transport Controls (GSMTC), если Ynison окажется недостаточно для конкретных сценариев.
- Интеграционный тест с альтернативными версиями Discord.
- Другие языки интерфейса.
- Обновление приложения через Tauri updater.

## 3. Ключевые технические решения

1. **Tauri 2 — оболочка desktop-приложения.** Vue не должен содержать бизнес-логику подключения к Ynison или Discord.
2. **Rust — единственное основное backend-ядро.** Не запускать sidecar на Node.js, Python или Go.
3. **Ynison — источник состояния воспроизведения в MVP.** Не делать периодические REST-запросы для выяснения текущего трека, если это состояние можно получать через WebSocket.
4. **Track ID — первичный ключ метаданных.** Не выполнять поиск по строкам при наличии ID трека.
5. **Discord RPC — отдельный адаптер.** Протокол/клиент Discord не должен быть размазан по состояниям Ynison или UI.
6. **Токен — только в системном хранилище секретов.** На Windows это Windows Credential Manager через поддерживаемый Rust crate или эквивалентную нативную интеграцию.
7. **Frontend получает снимок состояния и события.** Он не опрашивает Rust каждую секунду ради статуса соединения.
8. **Все внешние протоколы считать изменяемыми.** Ynison не является официальным публичным API с гарантией совместимости; сетевой слой должен иметь изолированный адаптер, фикстуры и понятную диагностику несовместимого ответа.
9. **Dynamic artwork — технический spike в самом начале.** Не считать, что Discord RPC гарантированно принимает произвольный URL в `large_image`. В первой фазе проверяется текущая совместимость клиента и используемой Rust-библиотеки. Должен оставаться рабочий fallback с ключом загруженного Discord asset или стандартной иконкой приложения.

### 4.2. Ответственность модулей

- `yandex::auth`: проверка/чтение токена, безопасное хранение и удаление; не содержит UI.
- `yandex::ynison_client`: жизненный цикл WebSocket, handshake, keep-alive, reconnect и преобразование сетевых ошибок.
- `yandex::protocol`: сериализация/десериализация сообщений и совместимость с протоколом; неизвестные поля не должны ломать разбор там, где возможно.
- `yandex::metadata`: получение недостающих метаданных по `track_id`, нормализация названия исполнителей, альбома, длительности и cover URL; запрос только при смене ID или истечении ограниченного кеша.
- `presence::coordinator`: единственная точка координации состояния playback, настроек и Discord.
- `presence::mapper`: чистая функция преобразования нормализованного playback state в модель Discord Activity.
- `discord::client`: соединение с локальным Discord IPC, handshake, публикация и очистка активности, переподключение.
- `config`: чтение/запись настроек без секретов, валидация и миграции схемы.
- `tray`: меню и команды system tray.
- `commands`: узкий Tauri API для UI. Команды не должны открывать произвольный доступ к файловой системе или системным секретам.

### 4.3. Модель выполнения

- Использовать async runtime Tokio с минимальным набором features, достаточным для WebSocket, таймеров и сетевых задач.
- Не включать `full` feature без обоснования.
- Долгоживущие задачи запускать через управляемый application state / task manager; при выходе приложения они должны корректно останавливаться.
- Не создавать новый поток или таймер на каждое событие playback.
- Предусмотреть cancellation token или эквивалентный механизм остановки задач при выключении приложения/отвязке аккаунта.
- Все сетевые вызовы имеют таймауты.
- Не блокировать UI thread и не выполнять долгие операции в Tauri command синхронно.

### 4.4. Жизненный цикл приложения

1. Инициализировать логирование и загрузить настройки.
2. Проверить наличие токена в Credential Manager без вывода его в логи.
3. Инициализировать system tray и окно.
4. Если `start_on_launch` включён и токен есть — запустить соединения автоматически.
5. Создать/запустить Ynison client.
6. Получить начальный snapshot playback state, затем принимать обновления протокола.
7. При появлении валидного трека запросить недостающие метаданные по ID.
8. Если Discord присутствует, публиковать активность; если Discord отсутствует — оставаться подключённым к Ynison и повторить подключение к Discord с backoff.
9. При закрытии окна не завершать приложение по умолчанию, а скрывать его в трей.
10. При явном `Quit` остановить задачи, очистить Presence (если IPC доступен), закрыть соединения и корректно завершиться.

## 5. Интеграция с Яндекс Музыкой

### 5.1. Авторизация

Для MVP реализовать ручной ввод OAuth-токена Яндекс Музыки, так как встроенная форма с паролем и имитация интерактивного входа создают лишние риски и усложняют поддержку.

Требования:

- Поле токена — password input, по умолчанию содержимое скрыто.
- Кнопки: `Проверить токен`, `Сохранить`, `Удалить токен`.
- До сохранения проверить токен тестовым запросом/инициализацией, не создавая постоянных сетевых циклов.
- При ошибке показать понятное сообщение (`токен не принят`, `нет сети`, `сервер временно недоступен`) без вывода самого токена.
- Токен хранить в Windows Credential Manager. Не сохранять его в JSON-настройках, `.env`, локальном storage, webview storage, аргументах процесса или логах.
- Передавать секрет из UI в Rust только через защищённую Tauri command; не помещать его в глобальный frontend store дольше, чем нужно для формы.
- После успешного сохранения очистить поле ввода и связанные значения из состояния UI.
- При удалении токена остановить Ynison, очистить текущий Presence и удалить запись из системного хранилища.
- Не запрашивать пароль Яндекса и не просить Discord user token.
- В документации объяснить, как пользователь получает/обновляет токен из доверенного источника. Не вставлять инструкции, ведущие к скачиванию неизвестных исполняемых файлов.

Если токен протух или сервер отклонил его — прекратить бесконечные повторные попытки с тем же секретом; показать состояние `Требуется повторная авторизация`.

### 5.2. Ynison

Использовать Ynison как основной real-time источник текущего воспроизведения. Ориентиры для изучения совместимости реализации:

- `https://github.com/FozerG/WinYandexMusicRPC` — Python-проект, полезный как reference по модели данных и последовательности действий.
- `https://github.com/thedvxch/yandex-music` — TypeScript-реализация API и realtime Ynison, полезная как дополнительный reference.

Не копировать слепо конкретную реализацию протокола. Агент должен проверить актуальные файлы, версии и лицензию, а затем реализовать Rust-адаптер с тестируемым протоколом.

Требования:

- Одно долгоживущее WebSocket-соединение, если актуальный протокол это позволяет.
- Выполнить корректный handshake и keep-alive согласно подтверждённой реализации протокола.
- Обработать полный цикл соединения: `Disconnected`, `Connecting`, `Connected`, `Reconnecting`, `AuthenticationRequired`, `ProtocolError`.
- Автоматически переподключаться с exponential backoff и jitter; использовать ограничение верхней задержки. Сбрасывать backoff после устойчивого соединения.
- Ответы должны разбираться устойчиво к неизвестным необязательным полям. Отсутствие второстепенного поля не должно завершать приложение.
- Отделить типы «сырого сообщения Ynison» от внутренней нормализованной модели.
- Не логировать исходные handshake payloads, токены, пользовательские идентификаторы или целые ответы, если они могут содержать персональные/секретные данные.
- Не выполнять REST-запрос к каталогу на каждом heartbeat.
- Метаданные по треку загружать при смене `track_id`/`playable_id`, а не при каждом обновлении позиции.
- Если в live-state уже присутствуют достаточные метаданные, не дублировать запрос.
- Предусмотреть ограниченный кеш метаданных по ID (LRU или аналогичный), ориентир — 100–300 записей, настраиваемый константой.
- Ошибки совместимости протокола логировать как структурированные диагностические события без секретов и показывать пользователю общую рекомендацию обновить приложение.

### 5.3. Нормализованная модель PlaybackState

Внутренний Rust тип должен быть примерно таким (имена и типы можно уточнить после проверки протокола):

```rust
struct PlaybackState {
    status: PlaybackStatus,        // Playing | Paused | Stopped | Unknown
    track_id: Option<String>,
    title: Option<String>,
    artists: Vec<String>,
    album: Option<String>,
    duration_ms: Option<u64>,
    position_ms: Option<u64>,
    cover_url: Option<Url>,
    track_url: Option<Url>,
    source_device: Option<String>,
    observed_at: SystemTime,
}
```

Обязательные требования к модели:

- Время хранить числом в миллисекундах и проверять на переполнение/отрицательные значения при парсинге.
- `artists` — список, не строка; строку для UI/Discord формировать одним централизованным mapper.
- `track_id` — непрозрачный идентификатор, не предполагать, что он всегда числовой.
- Валидировать URL обложки: только HTTPS и ожидаемые/настраиваемые разрешённые домены CDN Яндекса. Не разрешать произвольные scheme вроде `file:`, `javascript:`, `data:` и локальные адреса.
- `observed_at` нужен для оценки свежести; wall-clock время для логики тайминга по возможности не использовать вместо monotonic clock.
- Событие без track ID не должно приводить к панике; UI показывает нейтральное состояние или доступные метаданные.

### 5.4. Получение метаданных трека

Приоритет источников:

1. Полные метаданные в Ynison-состоянии.
2. Read-only endpoint каталога Яндекс Музыки по `track_id`.
3. Если метаданные недоступны — показать доступные поля и не пытаться искать похожий трек по названию.

Требования:

- Не использовать API Яндекс Музыки для загрузки аудио.
- Не хранить аудио и не скачивать его.
- При ошибке получения метаданных продолжать работу с данными live-state.
- Кешировать успешные метаданные ограниченно; не хранить их вечно и предусмотреть обработку частично заполненного кеша.
- На смене трека сбрасывать поля, которые относятся к предыдущему треку, чтобы старое название/обложка не мигрировали на новый трек.

## 6. Интеграция с Discord Rich Presence

### 6.1. Подключение

- Использовать desktop Discord IPC, а не Discord Bot API и не пользовательский токен.
- Предпочесть поддерживаемую Rust-библиотеку Rich Presence, например провести оценку `discord-rich-presence` и её текущих ограничений. Если библиотека не поддерживает нужное поле или корректное восстановление соединения, изолированно дополнить/заменить её адаптером, не распространяя собственный IPC-протокол на остальной код.
- Подключаться к локальным IPC endpoints Discord по документированному для Windows механизму.
- После успешного handshake сообщить UI `Discord подключён`.
- Если Discord закрыт, отображать `Discord не запущен` и периодически пробовать подключиться с backoff.
- После успешного переподключения повторно отправить актуальный Presence, если он должен быть включён.
- При выходе приложения попытаться очистить Activity, если Discord ещё доступен.

Документация Discord RPC: `https://github.com/discord/discord-api-docs/blob/main/developers/topics/rpc.mdx`.

### 6.2. Application ID

Rich Presence работает от Discord Application ID проекта. Application ID — публичный идентификатор, не секрет; его нельзя путать с bot token или user token.

- Хранить ID в единственной точке конфигурации сборки (например, build-time env или `config.rs`).
- Не дублировать ID строковыми литералами в нескольких модулях.
- Не включать фальшивый ID в релиз.
- Добавить `.env.example` или эквивалентный пример без секретов и описать, где создатель проекта получает Application ID.
- Если ID не задан, приложение должно собираться в dev-режиме с явным предупреждением, но не должно пытаться публиковать невалидную активность.
- В релизной конфигурации отсутствие ID должно приводить к понятной ошибке проверки конфигурации/сборки.

### 6.3. Отображаемые поля

Для активного трека:

- `type`: Listening (`2`).
- `details`: название трека.
- `state`: имена исполнителей, объединённые через `, `.
- `timestamps.start`: вычисляется по позиции трека, только когда таймер соответствует реальному воспроизведению.
- `assets.large_image`: динамическая обложка, только если подтверждено, что используемый RPC-путь/Discord client её поддерживает; иначе asset key, загруженный в Discord Developer Portal, или дефолтный image key.
- `assets.large_text`: название трека или альбом — в зависимости от доступной модели и ограничений.
- `buttons`: максимум одна кнопка в MVP — `Открыть в Яндекс Музыке`, если для трека построен и проверен корректный HTTPS URL. Если валидного URL нет, кнопку не отправлять.

Не отправлять пустые строки. Ограничивать длины строк безопасным пределом с учётом ограничений Discord RPC. Удалять управляющие символы и не допускать некорректного Unicode.

### 6.4. Пауза, остановка и очистка

- `Playing`: отправить активность с таймстампом старта, рассчитанным из позиции трека.
- `Paused`: если включена настройка `show_paused_tracks`, оставить название и исполнителя, обозначить паузу (например, в `state`) и удалить или заморозить таймстампы так, чтобы таймер Discord не продолжал идти. Поведение должно быть проверено в реальном Discord. Если невозможно отобразить фиксированную позицию стабильно — не отправлять таймстамп на паузе.
- `Stopped` или отсутствие текущего трека: очистить Discord Activity.
- `Unknown`: не затирать последнюю валидную активность мгновенно; действовать согласно стратегии свежести ниже.
- `Presence enabled = false`: немедленно очистить Activity и больше не отправлять обновления, пока опция не включена.
- После logout из Яндекс Музыки: очистить Activity и остановить Ynison.

### 6.5. Таймер и обновления

- Время Discord отображается на стороне клиента; не отправлять новое RPC-сообщение каждую секунду.
- Рассчитывать старт как `unix_now - floor(position_ms / 1000)` при воспроизведении.
- Если playback state содержит доверенную серверную временную метку или позиция изменилась существенно из-за seek, обновить таймстамп только при событии/существенном изменении.
- Не считать любое небольшое расхождение позиции новым событием.
- На паузе не допускать продолжающегося elapsed timer.
- Отправлять Presence при: старте/смене трека, изменении статуса Playing/Paused, существенном seek, изменении настройки, восстановлении Discord IPC.
- Добавить debounce/coalescing быстрых последовательных изменений в районе 250–500 мс, чтобы не спамить IPC во время смены состояния.

### 6.6. Политика очистки при сетевых сбоях

- При явном событии `Stopped` или пустом playback state очистить Presence без задержки.
- При потере Ynison соединения временно сохранить последнюю активность на короткое grace period (целевой ориентир 10 секунд), чтобы не мигать при кратковременном reconnect.
- Если валидное состояние не восстановлено после grace period, очистить Presence и показать `Нет актуальных данных`.
- Значение grace period держать в константе/настройке внутренней реализации и покрыть тестом.

### 6.7. Проверка динамической обложки — обязательный технический spike

До завершения основной реализации агент должен сделать небольшой прототип и проверить на реальном desktop Discord:

1. Публикацию Listening activity.
2. Отображение обычного текстового Presence.
3. Передачу URL обложки как `large_image` через выбранный IPC путь.
4. Поведение на отсутствующей/невалидной обложке.
5. Рабочий fallback на Discord asset key.

Результат зафиксировать в `docs/discord-artwork.md`: протестированные варианты, клиент/версия, успешный payload, ограничения и принятое решение. Не использовать прокси разработчика и не загружать обложки третьей стороне. Если URL не поддерживается, MVP должен оставаться функциональным с fallback asset. Не заявлять поддержку динамических обложек, пока она не подтверждена тестом.

## 7. Координатор состояния

Единый `PresenceCoordinator` объединяет:

- актуальный `PlaybackState`;
- состояние Ynison;
- состояние Discord IPC;
- пользовательские настройки;
- последнюю опубликованную Discord Activity;
- таймер grace period и политику debounce.

Он отвечает за решение, когда обновлять/очищать Discord Activity. Ни UI, ни сетевые адаптеры не должны самостоятельно посылать Discord Presence.

### 7.1. Примеры переходов

| Событие                            | Ожидаемое действие                                                         |
| ---------------------------------- | -------------------------------------------------------------------------- |
| Новый `track_id` и `Playing`       | Запросить недостающие метаданные, затем отправить Presence                 |
| Изменился только playback position | Не делать RPC update на каждый heartbeat; обновить локальную позицию/clock |
| `Playing` → `Paused`               | Обновить текст/таймстамп согласно настройке паузы                          |
| `Paused` → `Playing`               | Вычислить новый start timestamp и обновить Presence                        |
| `Stopped`                          | Очистить Activity                                                          |
| Ynison кратковременно отключился   | Сохранить последнюю активность на grace period                             |
| Ynison долго недоступен            | Очистить Activity и показать disconnect state                              |
| Discord закрылся                   | Пометить Discord disconnected, продолжить слушать Ynison                   |
| Discord снова запущен              | Подключиться и опубликовать актуальную активность                          |
| Пользователь выключил Presence     | Очистить Activity и игнорировать последующие события для публикации        |
| Пользователь удалил токен          | Остановить Ynison, очистить Activity, очистить секрет                      |

## 8. Модель настроек

Предлагаемая схема (может уточняться, но должна оставаться версионируемой):

```json
{
  "schemaVersion": 1,
  "presenceEnabled": true,
  "showPausedTracks": true,
  "showTrackTimestamp": true,
  "showAlbumArtwork": true,
  "startOnLaunch": false,
  "closeToTray": true,
  "minimizeToTray": true,
  "theme": "system",
  "language": "ru",
  "diagnosticsEnabled": true
}
```

Требования:

- В конфиге хранить только несекретные настройки.
- Не хранить OAuth-токен, Discord IPC payloads, содержимое аккаунта или историю проигрывания.
- Значения по умолчанию должны быть безопасными и пригодными для первого запуска.
- Проверять типы/значения при загрузке; некорректный конфиг не должен ломать запуск.
- Добавить `schemaVersion` и миграционный механизм на будущее.
- Записывать конфиг атомарно (temporary file + rename или надёжная библиотека хранения).
- Настройки должны сохраняться автоматически после изменения или после явной кнопки сохранения; поведение должно быть единообразным.
- Пользователь не должен терять настройки из-за временной сетевой ошибки.

Настройка `showTrackTimestamp` контролирует передачу таймстампов в Discord; она не означает, что приложение должно опрашивать API чаще.

## 9. Интерфейс и UX

### 9.1. Общие требования

- Современный компактный desktop UI: визуально аккуратный, с хорошей типографикой и иерархией, без избыточных карточек и тяжёлых эффектов.
- Vue 3 Composition API, TypeScript и Vite.
- Русский язык — основной язык MVP.
- Поддержка системной/тёмной/светлой темы; тема `system` должна учитывать системную настройку Windows, если это реализуемо стабильно.
- Не использовать браузерные alert/confirm; использовать встроенные dialog/toast компоненты.
- Все важные состояния доступны не только цветом: иконка + текст + корректные aria labels.
- Окно адаптивно минимум для 760×560 px; интерфейс не должен ломаться на увеличенном масштабе Windows 125–150%.
- Состояние кнопок и загрузки должно быть ясным; отключать повторный клик во время обработки команды.
- Не показывать токен полностью ни в одном состоянии UI.

### 9.2. Экран «Главная»

Основной экран должен содержать:

- Название приложения и индикатор общего статуса.
- Карточку `Сейчас играет`: обложка, трек, исполнители, альбом при наличии, продолжительность и локальный прогресс, если позиция доступна.
- Для отсутствующего трека — empty state с нейтральной иллюстрацией/иконкой и объяснением, что приложение ожидает воспроизведения в Яндекс Музыке.
- Состояния подключения к Яндекс Музыке и Discord, каждое со своим индикатором и короткой диагностикой.
- Главный toggle `Публиковать статус в Discord`.
- Кнопку перехода к настройкам токена, если токен не задан/отклонён.
- При проблеме — короткое человекочитаемое объяснение и действие `Повторить подключение`, когда оно применимо.

Не имитировать наличие трека, когда состояние неизвестно. Показывать `Не удалось получить данные` вместо выдуманных метаданных.

### 9.3. Экран «Настройки»

Группы:

**Discord Presence**

- Публиковать статус.
- Показывать трек на паузе.
- Показывать таймер воспроизведения.
- Показывать обложку, если поддерживается.

**Поведение приложения**

- Запускать вместе с Windows (по умолчанию выключено).
- Закрытие окна отправляет приложение в трей (по умолчанию включено).
- Минимизировать в трей (по умолчанию включено).
- Тема: системная / светлая / тёмная.

**Аккаунт**

- Состояние авторизации.
- Добавить/проверить токен.
- Удалить токен с обязательным подтверждением.

В настройках не должно быть полей Discord user token, bot token или пароля Яндекса.

### 9.4. Экран «Диагностика»

- Версия приложения.
- Версия Tauri/runtime, если доступна без лишних привилегий.
- Состояние Ynison: статус и время последнего успешного сообщения.
- Состояние Discord IPC.
- Последняя категория ошибки и время события.
- Кнопка `Открыть папку логов`.
- Кнопка `Скопировать диагностический отчёт`.

Диагностический отчёт должен удалять или маскировать OAuth-токен, любые заголовки авторизации, личные идентификаторы аккаунта, исходные секретные payloads и любые пути/значения, не нужные для диагностики. Перед копированием показать, что именно войдёт в отчёт, либо явно сказать, что секреты исключены.

### 9.5. System tray

Tray menu:

- `Открыть окно`.
- Статус `Discord подключён/не подключён` (только информация, если не поддерживается нативное отключение).
- `Публикация включена/выключена` — toggle.
- Разделитель.
- `Выход`.

Требования:

- Одиночный клик/двойной клик по иконке имеет единое понятное поведение.
- При закрытии главного окна процесс остаётся живым, если `closeToTray = true`.
- Пункт `Выход` действительно завершает приложение и все фоновые задачи.
- При повторном запуске не должно появляться несколько экземпляров. Реализовать single-instance plugin/механизм Tauri, если поддерживается выбранной версией.

## 10. Tauri security и IPC frontend/backend

### 10.1. Tauri commands

Минимальный интерфейс команд (имена могут отличаться, контракт — нет):

- `get_app_state()` — вернуть безопасный снимок состояния без секрета.
- `get_settings()` — текущие настройки.
- `update_settings(partial_settings)` — провалидировать и сохранить настройки.
- `validate_yandex_token(token)` — кратковременно проверить токен и вернуть безопасный результат; токен не возвращать.
- `save_yandex_token(token)` — положить токен в системное хранилище и запустить/перезапустить подключение по правилам приложения.
- `remove_yandex_token()` — остановить синхронизацию, очистить Presence и удалить токен.
- `reconnect_yandex()` — явная команда переподключения.
- `reconnect_discord()` — пересоздать Discord IPC connection.
- `set_presence_enabled(enabled)` — атомарно обновить настройку и соответствующее состояние Presence.
- `get_diagnostics()` — вернуть очищенный диагностический объект.
- `open_log_directory()` — открыть только заранее определённую папку логов.
- `quit_app()` — корректно остановить приложение.

Не открывать произвольные shell-команды из Vue. Не передавать frontend произвольный путь для чтения/записи. Не создавать generic `execute`, `read_file(path)` или подобные команды.

### 10.2. События Rust → Vue

Использовать события Tauri для важных изменений вместо периодического `invoke`:

- `app-state-changed` — соединения, авторизация и общий статус.
- `playback-changed` — нормализованное состояние трека.
- `settings-changed` — настройки после успешного сохранения.
- `notification` — безопасное уведомление уровня info/warning/error.

Не слать frontend каждое сетевое heartbeat-сообщение. Отправлять только значимые изменения. Обеспечить один lifecycle listener на компонент/приложение и корректно отписываться от listeners.

### 10.3. Capability model

- В `src-tauri/capabilities` задавать минимально необходимые права.
- Не включать широкие `fs:default`, shell или HTTP права frontend, если они не нужны.
- Сеть Ynison, запросы каталога, секреты и Discord IPC должны выполняться из Rust.
- CSP должен разрешать только необходимые origin для API/обложек; не ставить универсальный wildcard только ради удобства.
- Ссылки наружу открывать системным браузером с allowlist HTTPS URL, не навигировать основное окно на внешние сайты.
- Не отключать webview security ради решения проблем CORS; обложку можно отображать как изображение при достаточной CSP-политике.

## 11. Надёжность и обработка ошибок

### 11.1. Общие правила

- Ни одна сетевая ошибка не должна завершать приложение.
- Ошибки Rust преобразовывать в типизированную внутреннюю модель и затем в человекочитаемый текст/код для UI.
- Не показывать сырой stack trace в обычном интерфейсе.
- Повторные ошибки одинакового класса не должны спамить уведомлениями: использовать rate limit/coalescing.
- После ошибки система должна оставаться в восстанавливаемом состоянии.
- При выключении Presence не требуется поддерживать Discord activity, но состояние Ynison можно продолжать читать, если это нужно для моментального включения; выбранное поведение задокументировать и измерить. Рекомендуемое поведение для экономии ресурсов — при отключённом Presence останавливать ненужные запросы метаданных, но не пересоздавать WebSocket без необходимости.

### 11.2. Классы ошибок

- `NoToken` — токен не введён.
- `InvalidToken` / `TokenExpired` — требуется повторная авторизация.
- `YandexUnavailable` — сервис/сеть недоступны.
- `YnisonProtocolChanged` — ответ не соответствует ожидаемой схеме или handshake завершился ошибкой.
- `DiscordNotRunning` — Discord не запущен/IPC недоступен.
- `DiscordRpcError` — Discord отклонил Activity.
- `ArtworkUnavailable` — обложка отсутствует; не считать фатальной ошибкой.
- `SettingsReadWriteError` — настройки не удалось загрузить/сохранить.
- `SecretStoreError` — системное хранилище секретов недоступно.

### 11.3. Логирование

- Использовать структурированные уровни `error`, `warn`, `info`, `debug`.
- По умолчанию — уровень `info`, без потокового логирования каждого heartbeat.
- Ограничить размер/число log files или использовать ротацию.
- Не логировать OAuth-токен, HTTP Authorization headers, полные URL с секретными query params, сырые auth payloads, Discord user data.
- Дебаг-подробности можно включать в локальном dev-сборочном режиме; release-сборка не должна выводить секретные данные даже при ошибках.
- Не отправлять логи автоматически разработчику.

## 12. Производительность и память

### 12.1. Принципы

- WebSocket + event-driven processing вместо polling playback API.
- Один кеш метаданных с верхним пределом по числу записей.
- Дедупликация одинаковых запросов по track ID.
- Ограничение параллельных сетевых запросов, например не более 2–4 запросов метаданных одновременно.
- Ограниченные таймауты и отмена устаревшего запроса метаданных после смены трека, если он больше не нужен.
- Не создавать `setInterval` для backend polling каждые 100–1000 мс.
- Frontend timer прогресса активен только когда отображается окно и есть текущий трек/позиция; его выключение не должно менять Presence semantics.
- Использовать release build для оценки RAM; debug build не подходит для итоговых замеров.

### 12.2. Целевые ориентиры измерения

Проверить на чистом запуске Windows 10/11 x64:

- Память после стабилизации, когда приложение находится в трее и трек не играет.
- Память при активном воспроизведении.
- CPU в простое в течение 5 минут.
- Число сетевых запросов после запуска и при смене трека.
- Количество обновлений Discord IPC за одну минуту воспроизведения одного трека.

Начальные внутренние цели для review (не жёсткие аппаратно-независимые гарантии):

- После первичного запуска не должно быть регулярной заметной CPU-активности в простое.
- Во время одного неизменного трека не отправлять Discord Presence каждую секунду.
- В нормальном стабильном состоянии число REST-запросов метаданных — не более одного на track ID, кроме повторов после ошибок/протухания кеша.
- Не удерживать unbounded историю playback или unbounded cache.

В `docs/performance.md` сохранить методику и результаты измерений с указанием версии Windows, версии сборки и состояния Discord/WebView2.

## 13. Тестирование

### 13.1. Unit-тесты Rust

Обязательные группы:

1. Парсинг и нормализация Ynison fixtures.
2. Неизвестные дополнительные поля не ломают десериализацию.
3. Отсутствие title/artist/track ID обрабатывается без panic.
4. Построение Discord Activity для `Playing`, `Paused`, `Stopped`.
5. Проверка расчёта timestamps для разных `position_ms`.
6. Смена трека очищает метаданные предыдущего трека.
7. Кеш по track ID и ограничение его размера.
8. Backoff растёт, ограничивается максимумом и сбрасывается после восстановления.
9. Grace period: короткий disconnect не очищает Presence, долгий — очищает.
10. `presenceEnabled = false` очищает activity и запрещает дальнейшие update.
11. Ошибки secret store не приводят к утечке секрета в сообщениях.
12. Конфиг с неизвестными полями/неподдерживаемой версией не вызывает аварийное завершение.

Сетевые тесты должны использовать mock/fake server или записанные обезличенные fixtures; нельзя требовать рабочий токен разработчика для стандартного `cargo test`.

### 13.2. Frontend-тесты

- Пустое состояние без токена.
- Токен принят/отклонён.
- Ynison подключается/переподключается.
- Discord запущен/не запущен.
- Нет воспроизведения / Playing / Paused / ошибка сети.
- Переключатель Presence сразу отражает сохранённое backend состояние.
- Диалог удаления токена.
- Отображение длинных названий и нескольких исполнителей.
- UI на масштабировании Windows 125% и 150%.
- Не показывается токен или raw payload в компонентах и ошибках.

### 13.3. Integration/manual tests

Для завершения MVP обязательно проверить на реальном Windows desktop:

1. Яндекс Музыка воспроизводит трек — Discord показывает правильное имя трека и исполнителя.
2. Смена трека — Discord обновляется без длительной задержки и без старой обложки.
3. Пауза/возобновление — поведение соответствует настройке и таймер не убегает вперёд на паузе.
4. Остановка — Discord Activity очищается.
5. Discord закрыт при работающем приложении — UI показывает disconnected, приложение продолжает работу; запуск Discord восстанавливает Presence.
6. Кратковременная потеря сети — приложение переподключается.
7. Токен отклонён/удалён — показывается понятное состояние, старый Presence удаляется.
8. Закрытие окна — приложение остаётся в трее.
9. Выход через tray menu — процесс и соединения действительно завершаются.
10. Повторный запуск — не создаётся второй экземпляр.
11. Динамическая обложка — результат соответствует `docs/discord-artwork.md`; fallback работает.
12. Логи и diagnostic report не содержат токен.
13. Настройки сохраняются между перезапусками.

- Не реализовывать автообновление в MVP, если для него не настроен надёжный подписанный источник обновлений. При включении updater — следовать текущим требованиям Tauri и подписывать артефакты.
- Не включать токены, реальные данные пользователя или production credentials в CI artifacts.
- В `README.md` описать ограничения протокола Ynison и способ получить диагностический отчёт.

## 15. Зависимости и правила выбора библиотек

Агент должен проверить актуальные версии и совместимость перед добавлением зависимостей. Не выбирать библиотеку только по числу звёзд на GitHub.

Вероятные кандидаты (точный список выбрать в ходе реализации):

- Tauri 2 и официальный Vue starter/plugin ecosystem.
- Vue 3, TypeScript, Vite.
- Tokio — async runtime, только необходимые features.
- `tokio-tungstenite` или поддерживаемый WebSocket-клиент для Ynison.
- `serde`, `serde_json` для моделей.
- `url` для безопасной валидации URLs.
- `keyring` с подходящей feature-конфигурацией для Windows Credential Manager либо нативная Windows API реализация.
- Rust Discord Rich Presence IPC library после проверки текущей функциональности и licence; например, оценить `discord-rich-presence`.
- Официальные Tauri plugins только там, где они действительно нужны: tray icon/menu, autostart (для опции запуска с Windows), single-instance, updater (только если он в scope).
- `tracing`/`tracing-subscriber` и библиотека ротации/каталога логов по необходимости.
- Для тестов — стандартные Rust test framework и фронтенд test stack, совместимые с Vue/Vite.

Правила:

- Не добавлять два пакета, которые выполняют одну и ту же функцию.
- Не включать тяжёлую абстракцию для задачи, решаемой простой библиотекой.
- Проверить лицензию, актуальность и открытые security advisories для ключевых зависимостей.
- Не использовать `unsafe` без конкретной необходимости, локализации и комментария.
- Любой `unsafe` должен быть обёрнут безопасным интерфейсом и объяснён в code review.
- Не использовать `unwrap()`/`expect()` в production paths для сетевых, пользовательских или файловых данных; допустимы только для инвариантов, где это доказано тестами и ясно обосновано.

## 16. Этапы агентской разработки

Выполнять последовательно, но без ожидания одобрения после каждого технического шага. На каждом этапе сохранять компилируемое состояние и обновлять документацию.

### Этап 0. Исследование и technical spikes

- Проверить актуальный Tauri 2 scaffold для Vue + TypeScript.
- Прочитать исходники reference-проектов Ynison и изучить их лицензии.
- Определить минимальный рабочий handshake Ynison и состав live state.
- Прототип Discord IPC: handshake, LISTENING activity, clear activity.
- Проверить dynamic image/cover support и fallback.
- Выбрать библиотеки и записать решение в `docs/architecture-decisions.md`.

**Definition of Done:** описанный проверяемый результат spike, выбранные библиотеки и ограничения зафиксированы. Не начинать сложную UI-реализацию до подтверждения базового RPC-потока.

### Этап 1. Каркас приложения

- Создать Tauri 2 + Vue 3 + TypeScript проект.
- Добавить строгие TypeScript настройки, lint/format и release/dev команды.
- Создать Rust app state, безопасный invoke/event API и систему логов.
- Настроить Tauri capabilities/CSP по принципу минимальных разрешений.
- Реализовать окно, иконку, базовый tray и корректный quit lifecycle.

**Definition of Done:** приложение собирается в dev/release режиме; tray работает; повторный запуск не создаёт дубликат; тесты проходят.

### Этап 2. Авторизация и настройки

- Реализовать форму токена.
- Интегрировать Credential Manager через выбранную библиотеку/WinAPI.

**Definition of Done:** токен хранится только в credential store; токен не попадает в логи/config/frontend после сохранения; настройки сохраняются и валидируются.

### Этап 3. Ynison и метаданные

- Реализовать protocol adapter и WebSocket lifecycle.

- Реализовать backoff, keep-alive, cancellation и reconnect.

**Definition of Done:** на валидном тестовом/реальном аккаунте приложение определяет Playing/Paused/Stopped и текущий трек; автоматические unit-тесты не требуют real token; ошибки не завершают процесс.

### Этап 4. Discord Presence coordinator

- Реализовать Discord IPC adapter.
- Реализовать маппер Presence и координатор состояния.
- Внести политику pause/stop/timestamp/grace period/debounce.

**Definition of Done:** все переходы модели покрыты тестами; реальные manual tests подтверждают публикацию/очистку; Discord disconnect не ломает Ynison.

### Этап 5. Основной UI

**Definition of Done:** UI отражает фактическое состояние backend и не использует фейковые данные; все действия имеют обработку ошибок.

## 17. Критерии приёмки MVP

MVP считается готовым, когда все пункты ниже выполнены:

- [ ] Приложение устанавливается и запускается на Windows 10/11 x64.
- [ ] В приложении можно сохранить OAuth-токен Яндекс Музыки без запроса пароля аккаунта.
- [ ] Токен хранится в Windows Credential Manager или эквивалентном нативном credential store и не попадает в обычный конфиг/логи.
- [ ] Приложение подключается к Ynison и получает актуальное состояние воспроизведения.
- [ ] Название трека и исполнитель отображаются в UI без fuzzy matching.
- [ ] При Playing в Discord появляется Rich Presence типа Listening с корректными названием трека и исполнителем.
- [ ] При смене трека Presence обновляется; предыдущие метаданные не протекают в новую активность.
- [ ] Пауза, возобновление и остановка обрабатываются по заданной политике.
- [ ] Если Discord закрыт, приложение не падает и восстанавливает Presence после запуска Discord.
- [ ] Если Ynison временно недоступен, приложение повторно подключается с backoff.
- [ ] Переключатель Presence очищает активность сразу после выключения.
- [ ] Dynamic artwork проверен экспериментально, результат и fallback задокументированы.
- [ ] Закрытие окна отправляет приложение в tray, явный Exit завершает все задачи.
- [ ] После перезапуска сохраняются несекретные настройки.
- [ ] Есть диагностический экран/отчёт, который не раскрывает секреты.
- [ ] Unit tests и frontend checks выполняются локально без реальных токенов.
- [ ] Нет polling playback API каждую секунду и нет RPC update каждую секунду на неизменном треке.
- [ ] В репозитории имеются инструкции для dev build, release build и устранения типичных ошибок.

## 18. Указания coding-агенту

- Сначала изучи репозиторий и текущие версии зависимостей. Не предполагай, что legacy snippets актуальны без проверки.
- Не завершай задачу только созданием scaffold или красивого UI: ключевой deliverable — работающий поток `Ynison → нормализованный playback → Discord IPC`.
- Не подменяй реальные интеграции моковыми данными в production path. Моки допустимы только для тестов и UI preview.
- Не маскируй отсутствие поддержки dynamic artwork. Проведи spike и задокументируй реальный результат.
- Не добавляй ненужные функции и экраны вне scope.
- После каждого этапа запускай форматирование, lint, типизацию, unit-тесты и сборку; исправляй ошибки до перехода к следующему этапу.
- Любая неопределённость вокруг формата Ynison должна решаться чтением актуального reference-кода и фикстурами, а не придумыванием полей.
- Если реальная интеграция заблокирована отсутствием пользовательского токена или работающего Discord, реализуй воспроизводимые тесты на фикстурах и укажи конкретный ручной тест, который нужно выполнить. Не выдавай мок за подтверждённую интеграцию.
- Не коммить реальные токены/секреты. Не добавляй в приложение аналитику и сетевые endpoint разработчика.
- Не меняй архитектурный выбор Tauri + Rust + Vue на Electron, Wails, Go sidecar или отдельный backend.
- В финале предоставить: список реализованных функций, структуру проекта, команды запуска/сборки, результаты тестов, результаты artwork spike, замеры производительности и известные ограничения.
